# System Architecture

## Overview

The Real Estate Management System (REMS) is a full-stack web application designed to run on a private company LAN. There is no public internet exposure — all workstations access the same backend server over the local network.

```
LAN (192.168.x.x)
┌─────────────┐    HTTP/REST    ┌──────────────────┐    SQL     ┌──────────────┐
│ Workstation │ ─────────────► │  Express Backend  │ ─────────► │  MySQL/Maria │
│  (Browser)  │                │  :5000            │            │  :3306/3307  │
└─────────────┘                └──────────────────┘            └──────────────┘
      x N                              │
                              ┌────────┘
                              │  ./uploads/  (local disk)
                              │  ./logs/     (local disk)
```

In production, a single Express process on port 5000 serves:
- The React SPA (from `backend/public/` — generated by `npm run build`)
- All REST API endpoints (`/api/v1/*`)
- Uploaded static files (`/uploads/*`)
- Health check (`/health`)

## Request Lifecycle

```
HTTP Request
  → CORS check           (cors.js — LAN allowlist + RFC-1918 auto-allow)
  → Rate limiter         (express-rate-limit — 500 req/15min per IP)
  → Cookie parser        (cookie-parser — reads HttpOnly refresh token cookie)
  → Body parser          (express.json — max 10 MB)
  → Static files         (backend/public/ for SPA, backend/uploads/ for media)
  → Route match
      → authenticate     (JWT verification → req.user)
      → authorize        (role check → 403)
      → validate         (Joi schema → 422)
      → Controller
          → Model        (parameterised SQL via mysql2 pool)
  → Response helper      (standardised envelope)
  → errorHandler         (catches all unhandled errors)
  → SPA catch-all        (index.html for any non-API GET — production only)
```

## Authentication Architecture

```
Login
  → POST /auth/login
  → bcrypt.compare(password, hash)
  → signAccessToken()  — JWT, 8h, contains: id, uuid, email, role, name, jti
  → signRefreshToken() — JWT, 7d, contains same + unique jti
  → storeToken(userId, refreshToken)  — SHA-256 hash stored in refresh_tokens table
  → Set-Cookie: rems_rt=<token>; HttpOnly; SameSite=Strict; Path=/api/v1/auth
  → Response: { accessToken, refreshToken (also in body for API clients) }

Normal API request
  → Authorization: Bearer <accessToken>
  → authenticate.js: jwt.verify() → req.user
  → authorize.js: role check

Token Refresh
  → POST /auth/refresh (cookie sent automatically by browser)
  → jwt.verify(cookie token)
  → refreshTokenModel.verifyToken() — check hash in DB, not revoked, not expired
  → rotateToken() — revoke old (UPDATE revoked=1), insert new
  → Set-Cookie: rems_rt=<new token>
  → Response: { accessToken, refreshToken }
  → Old token immediately rejected (affectedRows check in UPDATE)

Logout
  → POST /auth/logout
  → refreshTokenModel.revokeToken(cookie token) — UPDATE revoked=1
  → clearCookie(rems_rt)
  → Old token returns 401 on next /auth/refresh
```

## User Roles

Roles are stored in the `users.role` ENUM column as `admin`, `manager`, or `agent`.
The application normalises `agent` → `employee` in JWT payloads and API responses.

| DB value | External label | Permissions |
|---|---|---|
| `admin` | admin | Full access — all modules + user management |
| `manager` | manager | All modules except user management |
| `agent` | employee | Own records only + read access to shared data |

Authorization is enforced by the `authorize()` middleware on every protected route — frontend hiding is supplementary.

## Database Architecture

- Engine: MySQL 8.x / MariaDB 10.4+
- All `DATETIME` columns store UTC
- UUIDs stored as `CHAR(36)` alongside auto-increment PKs
- Foreign key cascade: `CASCADE DELETE` for child media (images/videos); `SET NULL` for agent/employee references; `RESTRICT` for contract/financial references
- The `activities` table is append-only (audit trail)

### Tables

| Table | Purpose |
|---|---|
| `users` | System users (admin, manager, agent) |
| `property_types` | Lookup: Apartment, Villa, Land, etc. |
| `properties` | Property listings |
| `property_images` | Property photo gallery |
| `property_videos` | Property videos |
| `customers` | CRM leads and clients |
| `appointments` | Property viewing appointments |
| `contracts` | Sale/lease contracts (**schema present, module not yet implemented**) |
| `financials` | Payment records linked to contracts (**schema present, module not yet implemented**) |
| `activities` | Immutable audit log |
| `activity_log` | Legacy audit table (unused, kept for schema history) |
| `refresh_tokens` | Server-side refresh token revocation registry |

### Views

| View | Purpose |
|---|---|
| `v_properties_full` | Properties + agent name + image count + cover image |
| `v_customers_full` | Customers + assigned agent name |
| `v_dashboard_stats` | Single-row KPI snapshot for dashboard |

> **Note:** The `docs/database.md` documents triggers and stored procedures (`trg_*`, `fn_*`, `sp_*`). These are defined in `database/database.sql` but **are not present in the live database** as of this version — the live schema was built from migrations which do not include them. The application works correctly without them because the application layer handles these responsibilities (UUID assignment, contract numbering, etc.).

## LAN Deployment Notes

- Express binds to `0.0.0.0:5000` — all LAN interfaces.
- CORS: production mode accepts all RFC-1918 private addresses (`192.168.x.x`, `10.x.x.x`, `172.16-31.x.x`) plus the explicit `CORS_ORIGINS` list. This is correct for a closed company LAN.
- The built React SPA lives in `backend/public/` — served by Express.
- MySQL should run on the same host as the backend (`DB_HOST=127.0.0.1`).
- File uploads stored at `backend/uploads/` — served via Express static at `/uploads/*`.
- Google Fonts (Cairo + Poppins) are loaded from the internet. For offline deployments, see `docs/lan-setup.md` for the self-hosted fonts procedure.
